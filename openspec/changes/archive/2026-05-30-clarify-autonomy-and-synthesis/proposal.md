## Why

The `feature-workflow` skill's Clarify phase (1a) is a soft instruction: "ask targeted questions until every aspect of the feature is understood." Whether the model asks anything is left to its own self-assessment of input clarity. This works when input is visibly thin (one underspecified ticket — gaps are obvious). It fails when input is voluminous but vague: 9 loosely-related Jira tickets bundled as one feature produced a ~2000-word "scope" block that *looked* rich, so the orchestrator (Sonnet) self-assessed "I have the picture", asked zero questions, and proceeded to spec. The user had to bounce the spec+plan gate 3-4 times to correct compounding hallucinations.

Two structural problems caused this:

1. **Silent internal synthesis.** When the orchestrator does inference (merging multi-ticket bundles, re-slicing, inferring scope from sparse text), that synthesis is never externalized for user review before becoming the foundation for the spec.
2. **No agency over questioning posture.** The user has no way to tell the workflow "be chatty" or "don't bother me" up front. The model decides, and the model under-asks when input volume suggests false richness.

Three downstream defenses (sdd-expert's `openQuestions`, architect's `risks`, and the 1d gate) are all calibrated for "is the topic *mentioned*?" — not "is it *clear*?" They cannot recover what Clarify missed.

## What Changes

- **NEW phase 1-syn — Stated synthesis (always-fire, blocks).** Between ticket fetch (1-pre) and Clarify (1a), the orchestrator emits a 2-3 paragraph synthesis of its understanding of the feature. For multi-ticket input, the synthesis includes its proposed slicing. The orchestrator HALTS and waits for the user to confirm or correct. On correction, it re-synthesizes and re-blocks until confirmed. The Autopilot autonomy level (see below) is the only exception: it prints synthesis but does not block.

- **NEW autonomy lever at workflow entry — four levels.** After config validation and before 1-pre, the orchestrator prompts the user to choose a clarification autonomy level. Default sourced from `config.json` (`clarify.defaultAutonomy`, default `balanced`); user can override per invocation. Four levels:
  - `autopilot` — skip Clarify entirely; synthesis prints but does not block
  - `balanced` (default) — use enumeration rubric; ask about every "unclear" dimension
  - `guided` — ask only about direction-level dimensions (BE/FE, new vs refactor, scope boundary)
  - `manual` — free-form chat clarification; continues only on user "proceed"

- **REWRITTEN 1a Clarify — enumeration rubric replaces soft instruction.** For `balanced` and `guided` levels, the orchestrator MUST enumerate every clarification dimension and explicitly mark each `clear: <statement>` or `unclear: <what's missing>`. Every `unclear` becomes a question. Free-form "I think I have it" self-assessment is no longer permitted in these levels. `autopilot` skips this entirely; `manual` retains free-form chat.

- **REWRITTEN 1d gate payload — surfaces stated assumptions.** The gate request payload gains an "Assumptions" section listing any decisions the orchestrator made without asking (because autonomy level was `autopilot` or `guided`). This makes invented choices visible at the one mandatory human checkpoint, providing a safety net regardless of autonomy choice.

- **CONFIG addition — `clarify.defaultAutonomy`** in generated `config.json` files. Generated by `claudboard-workflow` with default `balanced`. Hand-editable by users.

- **TEMPLATE additions** — substitution variable `{{CLARIFY_AUTONOMY_DEFAULT}}` added to `substitution-catalog.md`; new section in `SKILL.md.template` for the autonomy prompt; new `### 1-syn` section; rewritten `### 1a` with rubric.

- **NO new capability flags.** The autonomy and synthesis logic ships in every generated `feature-workflow` regardless of project type. They are runtime levers, not template-time signals.

- **Scope guardrails (explicit):** Autonomy affects ONLY the clarification phase (1-syn, 1a, 1a-ws). The 1d gate ALWAYS fires for all autonomy levels. Implementation, review, and PR phases are UNAFFECTED.

## Capabilities

### Modified Capabilities

- `feature-workflow-generation`: Generated `feature-workflow` skills SHALL include the 1-syn stated synthesis phase, the autonomy-level entry prompt, the enumeration-rubric-based 1a Clarify, and the assumptions-surfacing 1d gate payload. The generated `config.json` SHALL include `clarify.defaultAutonomy` with default value `balanced`. The substitution catalog SHALL include `{{CLARIFY_AUTONOMY_DEFAULT}}` resolved from config or the static default.

## Impact

- **Files modified:**
  - `skills/claudboard-workflow/references/feature-workflow.template/SKILL.md.template` — new autonomy prompt section, new `### 1-syn` section, rewritten `### 1a Clarify scope` with rubric, modified `### 1d Gate` payload to include assumptions
  - `skills/claudboard-workflow/references/feature-workflow.template/config.json.template` — add `clarify.defaultAutonomy`
  - `skills/claudboard-workflow/references/substitution-catalog.md` — document `{{CLARIFY_AUTONOMY_DEFAULT}}`
  - `skills/claudboard-workflow/SKILL.md` — document the new generation behavior in the orchestrator's output description

- **Generated artifact behavior change:** Projects that have already run `/claudboard-workflow` will not automatically gain the new behavior. Per the documented "v1 has no upgrade path" caveat in `CLAUDE.md`, users must remove `.claude/skills/feature-workflow/` and re-run `/claudboard-workflow` to pick up the changes. The proposal documents this explicitly in the migration plan.

- **Out of scope (explicit):**
  - Implementing the underlying confidence-score computation (the four levels are discrete behavior bands; the UI can present them as a 0-100 slider but the backend always snaps to four bands)
  - Modifying any phase outside clarification (gate is touched only in payload — its blocking behavior is unchanged)
  - Changing model assignment for any agent (orchestrator remains Sonnet 4.6)
  - Auto-detection of when synthesis is needed (it always fires; cost is one extra exchange)

- **No version bump implied by this proposal alone** — minor bump appropriate at merge time per existing repo convention.
