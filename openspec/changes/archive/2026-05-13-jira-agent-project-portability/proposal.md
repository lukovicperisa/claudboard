## Why

The generated `feature-workflow` skill makes Jira-specific assumptions that work for Craftsphere but break on other Bosch projects. A real run on the MEAS project hung in the final phase (the "In Progress" / "In Review" status names are hardcoded and don't exist in MEAS's workflow), forced a `BE` area label that the project doesn't use, and silently destroyed the existing `Collaboration` label on the ticket. The workflow also has no way to signal a non-recoverable failure back to Jira, so failed runs leave tickets stuck "In Progress" with no observable signal.

## What Changes

- Replace hardcoded Jira status names (`"In Progress"`, `"In Review"`) in `jira-agent.md` and `SKILL.md.template` with abstract lifecycle states (`start`, `success`, `failure`, `pause`) that are resolved through a new `jira.transitions` block in `config.json`.
- Replace the hardcoded `Backend→BE / Frontend→FE / DevOps→DevOps / Docs→Docs` area-label map (currently embedded in agent prose) with a new `jira.labels.area` config field. `area: null` means no area label at all (the MEAS case); `area: { backend: "BE", frontend: null, ... }` allows a per-area map with nullable entries.
- Move the existing-label merge logic out of `jira-agent.md` and into the orchestrator (Sonnet). Add a new `applyLabels` action to jira-agent that takes a pre-computed list. Have `fetchAndPrepare` return `existingLabels` so the orchestrator can compute `{existing} ∪ {ai} ∪ {area_for_this_work}` itself. Reason: read-state → merge → write-back in plain prose is the kind of multi-step task Haiku flakes on.
- Add an orchestrator-level try/catch that fires `failure_transition` on **non-recoverable** failures only (MCP unavailable, transition lookup miss, ticket not found, network errors after retry, unhandled sub-agent exceptions). Recoverable issues — test failures, lint failures, design/spec review pushback, build failures — stay inside the existing iterate loop and do NOT poison ticket status.
- Add `pause` to the lifecycle-state config field as **reserved-for-future-use** (wired into config.json schema and prompts but no v1 command fires it). Documented as such in `jira-config-prompts.md` so future commands can hook in without re-touching every project's config.
- Update `jira-config-prompts.md` with prompt text, defaults (Craftsphere values), and "stub with TODO" escapes for all new fields. Defaults preserve current Craftsphere behavior — backward-compatible for any project regenerating with the same answers.

### Modified Capabilities
- `feature-workflow-generation`: `config.json` schema gains `jira.transitions` and `jira.labels` blocks; jira-agent template gains the `applyLabels` action and removes hardcoded transition/label vocabulary; the orchestrator (rendered `SKILL.md`) computes merged labels and references lifecycle-state names; Phase 2 config gathering gains new prompts; the rendered workflow wraps non-recoverable failures with a `failure_transition` call.

## Impact

- **Modified files** (in `skills/claudboard-workflow/references/`):
  - `feature-workflow.template/agents/jira-agent.md` — remove hardcoded transitions and area-label map; add `applyLabels` action; have `fetchAndPrepare` return `existingLabels`.
  - `feature-workflow.template/SKILL.md.template` — reference lifecycle-state names instead of literal Jira status strings; compute merged labels in orchestrator; wrap workflow with try/catch + `failure_transition` fallback.
  - `feature-workflow.template/config.json.template` — add `jira.transitions` and `jira.labels` blocks with Craftsphere defaults.
  - `jira-config-prompts.md` — add prompts for new fields with "reserved for future use" callout on `pause`.
  - `substitution-catalog.md` — only updated if a new `{{VAR}}` token is introduced (likely none — these go in config.json, not template substitution).
- **No source-code changes** to projects being onboarded. Template fix benefits future regenerations only.
- **Out of scope**: Updating hand-edited `feature-workflow/` skills already deployed in craftsphere.cloud, MEAS repos, or elsewhere — those are not regenerated by this change. Calling Jira APIs at generation time to discover real transition names is also deferred (heavier alternative considered and rejected for v1). No `/pause-feature` command is added.
- **Backward-compat note**: Projects that already ran `/claudboard-workflow` have a `config.json` without `jira.transitions` or `jira.labels`. Re-running on those projects requires removing the existing `feature-workflow/` directory first (per the existing v1 no-upgrade-path policy in CLAUDE.md). Defaults match Craftsphere so a re-run with the same answers preserves current behavior.
