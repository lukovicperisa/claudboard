## Context

The `feature-workflow` skill is generated by `claudboard-workflow` from templates under `skills/claudboard-workflow/references/feature-workflow.template/`. The Jira-related portions of the template were lifted from a hand-edited Craftsphere copy and inherited several Craftsphere-specific assumptions:

1. **Workflow column names.** Craftsphere uses `"In Progress"` and `"In Review"`. These names are written as literal strings in `jira-agent.md` and `SKILL.md.template`. MEAS uses `"Doing"` and `"Code Review"` — when the rendered workflow tried to fire a `transition` action with `targetStatus: "In Review"`, jira-agent's case-insensitive lookup against available transitions returned no match, the action emitted an error JSON block, and the orchestrator hung waiting for a successful result it would never get.
2. **Area-label vocabulary.** The `create` action body literally writes `"labels": ["<area_label>", "AI", "AI_CLI"]`, with `area_label` looked up from a fixed map embedded in the agent prose (Backend→`BE`, Frontend→`FE`, etc.). MEAS doesn't use `BE`. Other Bosch projects almost certainly have other taxonomies — or none at all.
3. **Label preservation.** `fetchAndPrepare` Step 3d documents a "merge existing + AI labels, dedupe" contract. In the MEAS run, `Collaboration` (an existing label on the ticket) was destroyed when AI/AI_CLI/BE were written. The `fetchAndPrepare` code path was confirmed via SKILL.md.template (user-supplied ticket keys go through it), so the merge logic itself is failing in practice. The most plausible cause: the prose instructs Haiku to "read existing → merge → write back" as a multi-step task, and Haiku is collapsing it to a single `editJiraIssue` call with the new labels list.
4. **No failure observability on the Jira side.** The current workflow only knows two transitions: into-progress at start, into-review at PR open. When something non-recoverable goes wrong — Atlassian MCP unavailable, transition lookup miss, network error after retry — the ticket is left in `In Progress` indefinitely with no signal anyone can act on.

The parent `claudboard-workflow` change is mid-implementation but has not archived yet; this change extends its `feature-workflow-generation` capability with new requirements about the rendered workflow's runtime behavior.

## Goals / Non-Goals

**Goals:**
- The rendered `feature-workflow` SHALL work on any Jira project with arbitrary workflow column names and arbitrary label conventions.
- The rendered workflow SHALL never destroy existing labels on a ticket.
- Non-recoverable failures SHALL leave the ticket in a status that signals the failure (when configured), instead of leaving it stuck mid-flow.
- Defaults SHALL preserve current Craftsphere behavior so a regenerated Craftsphere workflow with the same answers behaves identically.

**Non-Goals:**
- Updating the hand-edited `feature-workflow/` skills already deployed to Bosch repos. Per CLAUDE.md, v1 has no upgrade path; this change improves the template only.
- Implementing a `/pause-feature` command. The `pause` lifecycle state is added to config schema as **reserved-for-future-use** so future commands can hook in without re-touching every project's config, but no v1 command fires it.
- Auto-discovering real transition names by calling the Jira workflow API at generation time (option β from explore). That is heavier and adds Jira API calls during generation; deferred for now.
- Any change to ADO, git-agent, or pr-agent flows.

## Decisions

### Decision 1: Lifecycle states as the abstraction layer, not Jira status names

**Chosen:** Workflow code references abstract states — `start`, `success`, `failure`, `pause` — and `config.json` maps each to a project-specific Jira status name.

```jsonc
"jira": {
  "transitions": {
    "start":   "Doing",          // required
    "success": "Code Review",    // required
    "failure": "Blocked",        // optional, null = no-op
    "pause":   null              // optional, RESERVED FOR FUTURE USE
  }
}
```

**Why:** Decouples the workflow's intent from any one project's column names. The workflow says "begin work," not "transition to In Progress." Adding new lifecycle states later (e.g., `qa`) is a config-and-template change, not a project-by-project rewrite.

**Alternatives considered:**
- *Keep literal Jira status names but make them configurable strings (`config.transitionInProgress`, `config.transitionInReview`).* Rejected — leaks Jira's own vocabulary into the workflow, makes adding new states awkward, and doesn't naturally support `failure`/`pause`.
- *Auto-discover transition names from Jira at generation time.* Rejected for v1 — heavier, adds an API dependency to the generation flow, and doesn't help projects whose transition names change after generation. Could be added later as an opt-in enhancement.

### Decision 2: Area labels — per-area map with nullable entries, OR `null` for none

**Chosen:** `jira.labels.area` accepts either `null` (no area label ever — the MEAS case) or an object mapping each area to a label string or `null`:

```jsonc
"jira": {
  "labels": {
    "ai": ["AI", "AI_CLI"],
    "area": null,                    // form A: no area label ever
    "area": {                        // form B: per-area, null = skip that area
      "backend":  "BE",
      "frontend": "FE",
      "devops":   null,
      "docs":     null
    },
    "preserveExisting": true
  }
}
```

**Why:** Two real cases observed — MEAS uses no area label at all; Craftsphere uses BE/FE/DevOps/Docs. The two forms cover both cleanly without a third config shape. Per-area `null` lets a project use area labels for some work types but not others.

**Alternatives considered:**
- *Single `area` string field that applies to all work types regardless.* Rejected — Craftsphere needs different labels for different areas.
- *Mandatory map, no `null` shorthand.* Rejected — verbose for the MEAS case; users who don't use area labels would have to write `{backend: null, frontend: null, devops: null, docs: null}`.

### Decision 3: Move label merge from jira-agent (Haiku) to orchestrator (Sonnet)

**Chosen:** The orchestrator computes `{existing} ∪ {ai} ∪ {area_for_this_work}` and passes a fully-resolved labels array to jira-agent via a new `applyLabels` action. `fetchAndPrepare` returns `existingLabels` in its result block so the orchestrator has the inputs it needs.

**Why:** Read-state → diff → write-back as plain prose is exactly the kind of multi-step task Haiku reliably mishandles — observed in MEAS with the `Collaboration` label loss. Eliminating the LLM-doing-set-math problem entirely is more robust than tightening the prose.

**Alternatives considered:**
- *Rewrite the merge prose to be more explicit and step-by-step.* Cheaper but doesn't eliminate the failure mode — Haiku may still skip steps under load. The cost saving from using Haiku for set math is negligible compared to the harm of label loss.
- *Have jira-agent fetch existing labels itself before writing.* Same prose-fragility problem; doesn't change the underlying issue.

### Decision 4: Orchestrator-level try/catch, scoped to non-recoverable failures

**Chosen:** Wrap the workflow execution at the SKILL.md orchestrator level. On unhandled exceptions or sub-agent error result blocks for **non-recoverable** failures, fire `failure_transition` (if configured) and surface the error to the user.

**Recoverable vs non-recoverable**, decided explicitly:

| Category | Examples | Action |
|----------|----------|--------|
| **Non-recoverable** | Atlassian MCP unavailable, configured transition name not found in Jira's available transitions, ticket not found, network errors after retry, unhandled exception bubbling from any sub-agent | Fire `failure_transition`, surface error, halt |
| **Recoverable** | Test failures, lint failures, design review pushback, spec review pushback, build failures | Stay inside the existing iterate loop; do NOT touch ticket status |

**Why:** A failed test is a normal part of the iterate loop and shouldn't poison the ticket. A missing MCP server means the workflow cannot continue and the ticket should reflect that. The line between the two is "is this something the workflow itself fixes by iterating, or is it something the user must intervene on?"

**Alternatives considered:**
- *Wrap every step with its own try/catch.* Over-engineering; pushes failure handling into every phase prose.
- *Fire `failure_transition` on any error including recoverable ones.* Rejected — spam-thrashes the ticket through Blocked → In Progress → Blocked → ... on every iteration cycle.

### Decision 5: `pause_transition` is reserved-for-future-use

**Chosen:** Add the `pause` field to the config schema and the prompt flow, document it as reserved, but do NOT wire any v1 command to fire it.

**Why:** The current workflow has no explicit pause command. Adding the config field now is cheap and gives downstream commands a hook to use later without forcing every project to update its config. Defining the trigger and behavior fully now would be speculative.

**Alternatives considered:**
- *Drop `pause` from v1.* Adds churn later when a pause command is introduced — every project would need to add the field.
- *Define the trigger now (e.g., on `/squash-prep`).* Speculative; the right trigger isn't clear yet.

## Risks / Trade-offs

- [Risk] **Misconfigured transition name still errors** — if a user enters `transitions.start: "Doing"` but their Jira workflow has `"In Progress"`, the rendered workflow will still hit "no matching transition" and surface a non-recoverable failure. → Mitigation: this becomes a clear config error (caught by the orchestrator's failure path and surfaced to the user with the configured transition name and the list of available transitions), not a silent hang. Acceptable.
- [Risk] **MEAS bug-confirmation is presumptive on issue 3** — the merge-path code was confirmed by reading SKILL.md.template, but the user did not capture logs of the actual run, so "Haiku skipped the merge step" is the most plausible cause but not proven. → Mitigation: Decision 3 fixes the symptom regardless of cause by removing the prose merge entirely. If the cause was something else (e.g., a different code path), the new orchestrator-side merge still preserves labels.
- [Risk] **Backward compat for existing generated workflows** — projects that already ran `/claudboard-workflow` have a `config.json` without the new blocks. → Mitigation: this change targets the template only; per the existing v1 no-upgrade-path policy in CLAUDE.md, projects must remove the existing `feature-workflow/` directory and re-run. Defaults match Craftsphere so a re-run with the same answers preserves current behavior.
- [Risk] **Empty existingLabels edge case** — `fetchAndPrepare` on a ticket with no labels must return `existingLabels: []`, not omit the field. → Mitigation: Spec the return shape explicitly so the orchestrator's union math works on the empty case.
- [Risk] **Per-area area map adds prompting steps to Phase 2** — could feel verbose. → Mitigation: the top-level y/n short-circuits to `area: null` for projects that don't use area labels at all (probably the common case outside Craftsphere).
