## Context

The `feature-workflow` skill generated by `claudboard-workflow` orchestrates a deliberate, ticketed feature flow with exactly one user-facing gate (1d: spec + plan approval). The phases preceding the gate — ticket setup (1-pre), clarification (1a), spec writing (1b), and plan writing (1c) — run with the orchestrator inferring scope and the sub-agents producing artifacts based on that scope.

The current `### 1a. Clarify scope` text (`SKILL.md.template:659–674`) is a soft instruction:

> Ask targeted questions until every aspect of the feature is understood. … dig until the picture is complete.
>
> Things worth clarifying:
> - Which service is this for?
> - Is there a user-facing impact, …
> - [8 example dimensions]

There is no minimum-question floor, no per-dimension enumeration, no contract between the orchestrator and the user about "how much clarification is enough". The orchestrator (Sonnet 4.6) is left to self-assess whether it understands the feature. Sonnet is well-known to under-ask when context *looks* rich, even if the richness is surface-level. The 9-ticket failure mode is the demonstrated worst case: ~2000 words of concatenated ticket descriptions → model self-assessed "I have the picture" → zero questions → wrong spec.

Three downstream defenses exist but all fail the same way:
- **sdd-expert `openQuestions`** (`agents/sdd-expert-agent.md.template:282`) only triggers when ambiguities "cannot be resolved from the codebase or the provided scope" — vague-but-present scope statements satisfy the check.
- **architect `risks`** (`agents/architect-agent.md.template:648`) only flags blockers/unknowns the model itself notices.
- **1d gate** is the load-bearing safety, but it presents finished artifacts — the user has to reverse-engineer what was hallucinated.

This change replaces the soft instruction with a structural mechanism, and adds a synthesis step that externalizes the orchestrator's internal inference *before* it becomes the foundation for the spec.

## Goals / Non-Goals

**Goals:**
- Externalize the orchestrator's internal synthesis before Clarify, so silent inference (multi-ticket merging, scope re-slicing, sparse-text expansion) cannot become hidden spec foundations
- Give the user explicit control over questioning posture via a four-level autonomy lever at workflow entry
- Replace soft "ask until understood" with a per-dimension enumeration rubric in the default (`balanced`) level
- Preserve the 1d gate as a mandatory checkpoint for all autonomy levels
- Surface model-stated assumptions at the gate as a safety net for non-blocking levels

**Non-Goals:**
- Computing actual model-introspective confidence scores (the four levels are discrete bands; the UI can render a slider, but the system always snaps to bands)
- Changing any phase outside clarification (gate payload format gains an "Assumptions" section, but its blocking behavior is unchanged; implementation and review phases are untouched)
- Detecting "when synthesis is needed" (the 1-syn phase always fires; cost is one extra blocking exchange, except in autopilot)
- Auto-upgrading existing generated `feature-workflow/` directories (per repo convention: v1 has no upgrade path; users remove and re-generate)
- Switching the orchestrator model (remains Sonnet 4.6 — addressing the agreeable-Sonnet root cause via structural prompts, not model swap)
- Modifying sub-agent prompts (`sdd-expert-agent`, `architect-agent`) — their hatches remain; this change strengthens the upstream signal so the hatches are needed less often

## Decisions

### Decision 1: Synthesis is its own phase (1-syn), not a sub-step of Clarify

A new phase 1-syn sits between 1-pre (ticket setup) and 1a (Clarify scope). It always fires.

**Why a separate phase, not folded into 1a:**
- Clean separation of concerns: 1-syn handles "the model inferred something silently"; 1a handles "the model needs to ask about gaps". These are different failure modes with different fixes.
- The autopilot autonomy level can skip 1a entirely but still benefit from 1-syn (in non-blocking print mode).
- A phase boundary is visible in the workflow diagram and in `mcp__bosch__phase_start` instrumentation; clarifies what's happening for users and for cost/time tracking.
- Restructuring 1a is already significant; adding a sub-step would conflate two changes.

**Why always-fire (not "only when inference happened"):**
- Detecting "did inference happen" requires an introspective heuristic that the model can fail on (the same way Sonnet fails on confidence). Always-fire is honest and predictable.
- The cost is one extra round-trip; for the 9-ticket case it saves 3-4 gate bounces. Net win.
- The synthesis is useful as a contract even when input is crisp: it confirms the orchestrator understood single-ticket inputs the same way the user meant them.

**1-syn output shape:**
- 2-3 paragraph plain-English summary of the feature
- Multi-ticket only: proposed slicing list with one-line justifications
- Stated scope boundaries (what's in, what's out — best-effort from the orchestrator's reading)

**Blocking behavior:**
- All autonomy levels except `autopilot`: HALT and wait for user `confirm` or `correct: <feedback>`. On correct, re-synthesize, re-print, re-block.
- `autopilot`: print the synthesis as informational output, continue without blocking.

### Decision 2: Four-level discrete autonomy lever

Levels and behavior:

```
                 1-syn synthesis      1a Clarify behavior        1a-ws repos
                 ───────────────      ──────────────────         ───────────
autopilot (a)    print, no block      SKIP entirely              auto-confirm
balanced  (b)    print, BLOCK         enumeration rubric;        confirm only if
  (default)                           ask every "unclear"        any dim "unclear"
guided    (c)    print, BLOCK         direction-only rubric;     confirm only if
                                      ask only top-3 dims        direction unclear
manual    (d)    print, BLOCK         free-form chat;            always confirm
                                      continue on "proceed"
```

**Why four discrete bands (not a continuous knob):**
- Each band maps to genuinely different orchestrator behavior. Between-band granularity (e.g., "73%") has no honest mapping to behavior.
- UI surfaces can present a slider with named bands (snap or live-label) — the UX feels continuous while behavior is predictable.
- Discrete bands are easy to document in `SKILL.md.template` as conditional sections.

**Why these four (not three or five):**
- Three (autopilot / balanced / manual) loses the "ask only on direction" middle band that's useful for senior users who don't want micro-questions but do want direction confirmation.
- Five would split balanced or add a "minimal" band; not clear what additional behavior that buys.

**Default = `balanced`:**
- Matches current implicit behavior most closely (the workflow expects to ask questions; we're just making "ask" structural instead of vibes-based).
- Conservative default; users who want less questioning explicitly opt down.

**Naming rationale:**
- `Autopilot ↔ Manual` is the cleanest universally-understood opposite pair (driving metaphor).
- `Balanced` and `Guided` fill the middle with intuitive labels that don't require explanation.
- `Co-pilot` was considered and rejected (Microsoft product baggage; metaphor is ambiguous about whether the AI or the user is the co-pilot).

### Decision 3: Enumeration rubric for `balanced` and `guided`

The `balanced` level requires the orchestrator to enumerate every dimension and mark each `clear` or `unclear` before any question is asked. The current 8 example dimensions become the canonical rubric:

```
Dimensions (balanced):
  1. Target service / repo
  2. User-facing impact (internal vs external)
  3. Constraints and related tickets
  4. Actors and roles
  5. Error and edge cases
  6. Authorization requirements
  7. Integration/event boundaries
  8. Input validation rules
```

For each dimension the orchestrator emits either:
- `clear: <one-sentence statement of what it understands>`, or
- `unclear: <one-sentence statement of what is missing>`

Every `unclear` becomes a question to the user. The orchestrator MAY NOT skip questions for dimensions it marked unclear. The rubric is re-evaluated after user answers; questioning continues until every dimension is `clear`.

The `guided` level uses a reduced rubric:

```
Dimensions (guided):
  1. Target service / repo  (direction-level: which codebase)
  2. Change shape (new feature / refactor / bugfix / removal)
  3. Scope boundary (what's in, what's deferred)
```

Dimensions 4-8 from the balanced rubric are deferred to sdd-expert's `openQuestions` and architect's `risks` (the existing downstream hatches).

**Why a structured rubric rather than a question count floor:**
- Question count floors are gamable ("ask 3 trivial questions to satisfy the floor"). Rubric coverage forces useful asks.
- The rubric makes orchestrator reasoning visible and auditable — the user can see what the orchestrator thinks is clear and push back if it's wrong.
- The rubric is the same data structure across autonomy levels; only the threshold for asking changes. Simpler to implement than four different question patterns.

### Decision 4: Gate payload gains an "Assumptions" section

The 1d gate payload (currently `{ kind, payload: { ticket, spec, plan } }`) gains a fourth payload field:

```json
{
  "kind": "spec+plan",
  "payload": {
    "ticket": "<key>",
    "spec": "<full spec text>",
    "plan": "<full plan text>",
    "assumptions": "<markdown list of decisions made without asking>"
  }
}
```

Assumptions are populated by the orchestrator when:
- Autonomy was `autopilot` (Clarify skipped — every dimension is an assumption)
- Autonomy was `guided` (dimensions 4-8 were not asked — their resolution is an assumption)
- Autonomy was `balanced` or `manual` but synthesis correction by the user changed only some interpretations (any remaining inferred interpretation is an assumption)

In `balanced` and `manual` with no corrections, the assumptions list MAY be empty.

**Why this is the safety net:**
- It makes invented choices visible at the one mandatory checkpoint, regardless of which autonomy level was used.
- It costs nothing for `manual` users (empty list); it pays back for `autopilot` users (full enumeration of what was inferred).
- It does not change the blocking behavior of the gate (still binary approve/reject) — only the surface area.

### Decision 5: `config.json` gains `clarify.defaultAutonomy`

Generated `config.json` includes:

```json
{
  "jira": { ... },
  "git": { ... },
  "clarify": {
    "defaultAutonomy": "balanced"
  }
}
```

The orchestrator at workflow entry reads this default, presents it to the user, and accepts a one-letter override (`a` / `b` / `c` / `d`).

**Why config-side default with per-invocation override:**
- Per-invocation prompt only ("ask every time") adds friction; many features want the same posture as the project default.
- Config-side only ("set and forget") doesn't match the moment — a complex feature on a project default of `autopilot` is a mistake the user can't easily catch.
- Hybrid (default + 1-line confirm) is the lowest friction with the highest safety.

**Why `balanced` as the static default in the template:**
- Generated skills should be safe for new users who don't know the levels exist.
- A user can lower the default for their project after they've built confidence; the system shouldn't ship "low ceremony" by default.

### Decision 6: No new template capability flags

The new behavior (1-syn phase, autonomy prompt, rubric-based 1a, gate assumptions) ships in every generated `feature-workflow` regardless of the project's detected stack or signals. There is no `<!-- IF SYNTHESIS_GATE -->` or similar.

**Why:**
- The behavior is universally useful across all project types — there is no detected signal that says "this project doesn't need synthesis".
- Adding a flag implies the behavior is optional at generation time, when actually we want it on for everyone with runtime control via autonomy levels.
- One substitution variable (`{{CLARIFY_AUTONOMY_DEFAULT}}`) is enough to parameterize per-project defaults.

## Risks / Trade-offs

- **[Risk] Synthesis blocking adds friction for users who currently like the autonomous flow.** → **Mitigation:** `autopilot` autonomy level explicitly supports non-blocking synthesis (informational print only). Users who want the current flow can set `clarify.defaultAutonomy: "autopilot"` in their config.

- **[Risk] Enumeration rubric in `balanced` may produce noisy question lists for trivial features.** → **Mitigation:** dimensions marked `clear` produce zero questions; for simple features most dimensions will be `clear` from the ticket text alone. Users who systematically find balanced too noisy can default to `guided` per-project. We monitor real usage and tune the dimension list if real cases show systematic over-asking.

- **[Risk] Users default the project to `autopilot` to avoid friction and then forget — re-introducing the original failure mode.** → **Mitigation:** workflow entry prints the resolved autonomy level visibly (e.g., "Clarification autonomy: autopilot — skipping clarification questions"). The gate payload's `assumptions` section makes invented decisions visible regardless. The user can interrupt synthesis-print in autopilot mode if it scrolls past wrong.

- **[Risk] Multi-ticket synthesis quality depends on the orchestrator's Sonnet-tier reasoning — wrong synthesis blocks until user corrects, but a subtly-wrong synthesis may pass user inspection.** → **Mitigation:** the synthesis explicitly states the orchestrator's proposed slicing for multi-ticket input, surfacing the high-leverage decision. Subtle errors remain a residual risk but are caught at the 1d gate (smaller blast radius than today — model has been corrected upstream at least once).

- **[Risk] Changing the gate payload format breaks any downstream consumer (bosch web UI for gate display).** → **Mitigation:** `assumptions` is an additive field; the existing `spec` and `plan` fields are unchanged. UI consumers that don't render `assumptions` are unaffected.

- **[Risk] Existing generated `feature-workflow/` directories don't auto-upgrade.** → **Mitigation:** this is the standing repo convention (`CLAUDE.md`: "v1 has no upgrade path"). The change documents the regeneration command. We accept the cost.

- **[Trade-off] Autonomy lever applies only to clarification, not to implementation interrupts.** Some users may want check-ins between implementation checkpoints. Decision: keep implementation phase unaffected — the explicit scope guardrail per the explore session. Implementation autonomy is a separate concern that can be a follow-up change.

- **[Trade-off] Four discrete bands vs continuous knob.** UI-side a slider sells better; backend-side discrete bands are more predictable. Compromise: backend always snaps to four bands; UI can render a slider with band labels. Documented in `block-catalog.md` as a band-mapping rule.

## Migration Plan

This is a template-only change: it modifies what `/claudboard-workflow` generates, not any runtime data store.

**For new projects (post-merge):**
- Run `/claudboard-workflow` → generated `feature-workflow/` includes the new behavior by default
- Default `clarify.defaultAutonomy` is `balanced`
- User can edit `config.json` to change the project default

**For existing projects with previously-generated `feature-workflow/`:**
- Per the standing v1 caveat in `CLAUDE.md`: remove `.claude/skills/feature-workflow/` and re-run `/claudboard-workflow`
- The completion report from `claudboard-workflow` already prints the regeneration command; no new tooling needed

**Backward compatibility:**
- Existing `config.json` files (without `clarify.defaultAutonomy`) — orchestrator defaults to `balanced` when the field is missing
- Existing gate payload consumers — `assumptions` is additive, ignored by old consumers
- No data migration needed (no persistent runtime state changes)

**Rollback:**
- Revert the change. Existing generated `feature-workflow/` directories that have the new behavior continue to work standalone (they're self-contained template output). Future regenerations revert to old behavior.

## Resolved Questions

All open questions from initial design were resolved during the explore session.

- **Autonomy override persistence across invocations: ONE-SHOT.** Per-invocation override applies only to that invocation; next invocation re-prompts with the config default. Persistence would mask drift between user intent and project default. To change the project default, the user edits `config.json` directly.

- **Per-feature autonomy memory: NO MEMORY.** Each `/start-feature TICKET-X` invocation is a fresh session. Autonomy comes from project default plus per-invocation override only. The change directory under `.claude/changes/<TICKET>/` does NOT store autonomy state. Carrying state across sessions adds complexity for marginal benefit.

- **Guided mode and multi-ticket slicing: CONFIRM BOTH.** Guided mode is designed to ask about direction-level decisions, and proposed slicing is the highest-leverage direction decision in multi-ticket input. The synthesis confirmation in guided mode therefore covers both the prose summary AND the proposed slicing in a single blocking exchange.

- **Ambiguous user `correct: <feedback>` responses: ASK A CLARIFYING QUESTION, do not guess.** If the orchestrator cannot derive a concrete change from the user's correction (e.g., "this is wrong" with no specifics), it MUST ask a targeted clarifying question before re-synthesizing. This avoids spinning the correction loop on guesses.

- **Synthesis grounding in project context: READ WHEN AVAILABLE.** Phase 1-syn reads `CLAUDE.md`, `.claude/memories/ecosystem.md` (or equivalent), and (in workspace mode) per-repo analysis reports BEFORE synthesizing, when those files exist. This grounds the synthesis in what the project actually does, catching "the ticket sounds like X but X doesn't exist here" mismatches. When the files are absent, synthesis falls back to ticket text only.
